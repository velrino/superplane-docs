Use this page to preserve data before maintenance and remove only the resources from your installation. A [single VM](/self-hosting/single-vm) uses the release package. A [cloud install](/self-hosting/install) uses Terraform.

## Back up a single VM

Use a backup procedure that you tested for your environment. Before maintenance:

- Stop new work and wait for current tasks to finish.
- For a cold backup, stop local runners and all Compose services before you copy volumes.
- Preserve the installation configuration, original secrets, OIDC keys, and all project data volumes.
- Record the release, component images, architecture, hostname, and Compose project.
- Keep a verified copy outside the VM with restricted access.

Do not copy live PostgreSQL files as a cold backup. Test restoration before you rely on the backup.

### Restore a single VM

Confirm these conditions before restoration:

- The archive is trusted and its checksums pass.
- The original release, component images, and architecture are available.
- The target installation is stopped and its data volumes are empty.
- The original configuration, secrets, ownership, and file permissions can be restored.

Check service health, owner access, and restored data before you accept new work. Do not generate replacement secrets for data encrypted with the original values.

## Upgrade a single VM

Back up the installation first. Select the target [SuperPlane release](https://github.com/superplanehq/superplane/releases) and follow the [download and checksum steps](/self-hosting/single-vm#2-download-the-release). Use the checksum file from that target release.

From the existing installation directory, replace the Compose file and packaged scripts. Keep the existing environment files, `oidc/`, and `Caddyfile`. Set the archive path below to your verified download:

```bash
release_dir=$(mktemp -d /tmp/superplane-release.XXXXXX)
tar -C "$release_dir" -xzf /absolute/path/superplane-single-host.tar.gz
cp "$release_dir/superplane/docker-compose.yml" .
for script in install.sh uninstall.sh diagnose.sh; do
  if [ -f "$release_dir/superplane/$script" ]; then
    cp "$release_dir/superplane/$script" "./$script"
    chmod +x "./$script"
  fi
done
./install.sh
```

The installer keeps existing secrets and regenerates derived configuration, including `fleet-manager.yaml` and `rabbitmq.env`. It pulls the packaged images and starts database migrations with the application. Use the [installation checks](/self-hosting/single-vm#4-verify-the-installation), then confirm owner access and existing data.

Do not assume that replacing an image with an older version reverses a database migration. Keep the original backup until you validate the upgrade. If recovery is necessary, restore the complete backup with its original release.

## Uninstall a single VM

Stop new work and wait for current tasks to finish. Run removal commands from the installation directory. Container removal does not delete the VM or its cloud disks.

### Packages with `uninstall.sh`

Use this section only if your release package includes `uninstall.sh`. The `v1.0.0-rc7` package does not include it; use the manual procedure below.

By default, the script removes this installation's services, managed runners, and project network. It preserves named data volumes and host configuration. It refuses running runners unless you explicitly allow their interruption with `--force`.

When you preserve data, the application API must be available to retire this installation's runners. The script waits up to 60 seconds for retirement before it removes runner containers. If retirement fails, the application and runner containers remain; run `./install.sh` to resume before you retry.

After you verify that work is finished, remove the installation while preserving its data:

```bash
./uninstall.sh --force
```

Review the confirmation before you continue. The `--force` flag permits cancellation; it does not guarantee immediate cancellation or drain work automatically. The separate `--yes` flag skips confirmation for an unattended command.

Run `./install.sh` from the same directory to resume with the preserved data and configuration.

Choose preservation or purge before removal. If you already removed the services while preserving volumes, resume the installation before you use `--purge`. The script requires ownership information from existing Compose containers before it deletes retained volumes.

<Aside type="danger" title="Purge deletes project data">
Copy a verified backup off the VM first. The `--purge` option also deletes this installation's named volumes. It keeps host configuration and secret files.
</Aside>

To remove the installation and its project data, use:

```bash
./uninstall.sh --force --purge
```

Delete retained configuration and secrets only after you verify the backup and decide not to resume this installation.

### Packages without `uninstall.sh`

Fleet Manager starts runner containers outside Compose ownership. A Compose removal command can return success while a runner keeps the project network in use.

Stop Fleet Manager so it cannot replace a runner during removal. Then stop the application so it cannot assign queued work. List the Compose services and managed runners:

```bash
docker compose --profile runners stop fleet-manager
docker compose --profile runners stop app
docker compose ps --all
docker ps -a --filter label=superplane.managed-runner=true \
  --format 'table {{.ID}}\t{{.Names}}\t{{.Networks}}'
```

The runner list can include other installations. Inspect each candidate's fleet label and network, then verify that network's Compose project label:

```bash
docker inspect your_runner_container_id \
  --format '{{json .Config.Labels}} {{json .NetworkSettings.Networks}}'
docker network inspect your_installation_network \
  --format '{{json .Labels}}'
```

Remove only the exact runner IDs that you verified for this installation. Repeat these commands for each verified runner:

```bash
docker stop your_runner_container_id
docker rm your_runner_container_id
```

Remove the Compose services and project network while preserving named volumes:

```bash
docker compose --profile runners down --remove-orphans
```

To delete project volumes too, add `-v` only after you copy a verified backup off the VM. Confirm that the selected runners and project network are absent. If removal reports a network still in use, inspect its attached containers before you continue. Do not use a global Docker prune command.

After you resume an installation with preserved data, check both running runner containers and API capacity with the [diagnostic checks](/self-hosting/troubleshooting#collect-single-vm-diagnostics). The preserved database can retain stale runner records until reconciliation.

## Upgrade a cloud install

1. In your Terraform checkout, set `superplane_chart_version` to `@@SUPERPLANE_CHART_VERSION@@`. Leave `superplane_image_tag` empty. The chart version has no `v` prefix. Move to a newer Terraform installer tag only when the release notes require it.
2. Set the new runner image IDs from the release notes. On Google Cloud, build a new image with Packer when the runner tools change, or keep the current image. `runner_image_amd64` must not be empty while runners are enabled. Google Cloud now enables runners and GCS blob storage by default. To keep an older install without them, set `enable_runners = false` and `enable_gcs_blob_storage = false`.
3. Apply, then run the Fleet Manager Helm command from **Fleet setup** again. Set `image.tag` to `@@FLEET_MANAGER_VERSION@@`. Set every `runnerVersion` to `@@RUNNER_VERSION@@`. Set Helm `--version` to `@@FLEET_MANAGER_CHART_VERSION@@`. Do not install a newer Fleet Manager chart or Runner.

```bash
terraform plan -out tfplan
terraform apply tfplan
```

4. Confirm the installation:

```bash
kubectl get pods -n superplane
kubectl get certificate -n superplane
```

To change how many runner machines stay up, edit `warmCapacity` and `maxCapacity` in `fleet-manager-values.yaml` and run that same Helm command. Each AWS or Azure machine uses 2 vCPUs. The Google Cloud default machine type uses 4.

## Uninstall a cloud install

Export anything you need first. This deletes the cluster, the database, and file storage.

<Aside type="danger" title="Uninstall deletes the installation">
Disable every fleet and wait until tasks finish and warm capacity is 0. Terminate runner machines that are still running. They are not in the Terraform state, and the cloud account keeps billing them.
</Aside>

<Tabs syncKey="cloud">
  <TabItem label="AWS">

```bash
export AWS_REGION=us-east-1
FLEET_MANAGER_ID=$(helm get values fleet-manager -n superplane --all --output json | jq -er '.manager.id')
RUNNER_INSTANCE_PROFILE_ARN=$(aws iam get-instance-profile \
  --instance-profile-name "$(terraform output -raw runner_instance_profile_name)" \
  --query 'InstanceProfile.Arn' --output text)
helm uninstall fleet-manager -n superplane
```

Set `AWS_REGION` from `region` in `terraform.tfvars`. Terminate any instances that are still running:

```bash
aws ec2 describe-instances --region "$AWS_REGION" \
  --filters "Name=tag:superplane_fleet_manager_id,Values=${FLEET_MANAGER_ID}" \
    "Name=iam-instance-profile.arn,Values=${RUNNER_INSTANCE_PROFILE_ARN}" \
    "Name=instance-state-name,Values=pending,running,stopping,stopped" \
  --query 'Reservations[].Instances[].InstanceId' --output text
```

Turn off RDS deletion protection, apply that change, and empty the S3 bucket from `terraform output -raw blob_storage_bucket`:

```hcl
rds_deletion_protection = false
```

```bash
terraform plan -target=aws_db_instance.superplane -out tfplan
terraform apply tfplan
```

  </TabItem>
  <TabItem label="Azure">

```bash
helm uninstall fleet-manager -n superplane
az vm list -g "$(terraform output -raw runner_resource_group)" -d -o table
```

Delete any `sprunner-` virtual machines that remain.

  </TabItem>
  <TabItem label="Google Cloud">

```bash
helm uninstall fleet-manager -n superplane
```

Turn off deletion protection, then destroy. Terraform does not delete the static IP.

```hcl
gke_deletion_protection   = false
sql_deletion_protection   = false
blob_bucket_force_destroy = true
```

```bash
terraform plan -out tfplan
terraform apply tfplan
terraform plan -destroy -out tfplan
terraform apply tfplan
gcloud compute addresses delete superplane-ip --global
```

  </TabItem>
</Tabs>

On AWS and Azure, destroy after the steps in the tab:

```bash
terraform plan -destroy -out tfplan
terraform apply tfplan
```

`terraform apply tfplan` deletes resources because the plan is a destroy plan. If the AWS destroy stops on the load balancer, use the [AWS installer README](https://github.com/superplanehq/terraform/blob/v0.1.0/aws/README.md#destroy). Do not delete the Terraform state while a destroy is incomplete.
